# dashgen v0.4 — Iteration Queue

**Status:** pre-planning. Captures carry-overs from v0.3.0 and immediate post-release work. Not a sequenced plan yet — items get pulled into a V0.4-PLAN.md once scope and order are agreed.

**Predecessor:** v0.3.0 shipped 2026-04-29 with the YAML+CUE+text/template recipe DSL and 4-platform binaries. See [V0.3.0-VERIFICATION-REPORT.md](V0.3.0-VERIFICATION-REPORT.md) for the green-light evidence and [V0.3-PLAN.md](V0.3-PLAN.md) for the full migration arc.

---

## 1. Carry-overs from v0.3.0 (small, do first)

### 1.1 ldflags version injection

**Why:** `dashgen version` (if/when it exists) currently reports an empty string because `cmd/dashgen/main.go` has no `var version` and `.goreleaser.yaml` has no `-X main.version=…` ldflags. T8.2 noted this; T8.3 verifier flagged as v0.4 follow-up.

**Scope:** ~30 LOC.

- Add `var version = "dev"` to `cmd/dashgen/main.go` (or wherever the entrypoint lives).
- Add `ldflags: ["-s", "-w", "-X main.version={{.Version}}"]` to the `builds:` stanza in `.goreleaser.yaml`.
- Bonus: add a `dashgen --version` flag (or `dashgen version` subcommand) that prints the value.

**Acceptance:** `dashgen --version` from a `release-dryrun.sh` archive prints something like `0.4.0-snapshot-<sha>` or, in real releases, `0.4.0`.

### 1.2 Sanity-check the v0.3.0 release artifacts

Once `.github/workflows/release.yml` finishes running on the v0.3.0 tag push, manually confirm:

- 4 archives + checksums.txt are attached to the GitHub release page.
- One archive (e.g. `dashgen_0.3.0_darwin_arm64.tar.gz`) extracts cleanly and the binary `--help` works on a clean machine.
- The release-page URL pattern in [README.md](../README.md) actually resolves.

If anything is broken, ship a **v0.3.1 patch** with the fix rather than dragging it into v0.4.

## 2. Distribution coverage (deferred from V0.3-PLAN T8.2)

V0.3-PLAN T8.2 explicitly punted these to v0.4:

### 2.1 macOS code signing + notarization

**Why:** v0.3.x macOS binaries trigger Gatekeeper warnings. README.md documents this as a known v0.3 limitation.

**Scope:** non-trivial. Apple Developer ID + Apple Notary Service + entitlements + the `notarytool` workflow. Estimated multi-day; needs an Apple Developer account.

**Suggested approach:** add a separate workflow file that signs+notarizes after the existing release.yml finishes. Don't merge into release.yml until proven.

### 2.2 Homebrew tap

**Why:** macOS users expect `brew install dashgen` to work.

**Scope:** small once the auto-bump pipeline exists. goreleaser has built-in homebrew formula generation — usually a `brews:` stanza in `.goreleaser.yaml` plus a tap repo (e.g. `homebrew-dashgen`) and a `HOMEBREW_TAP_GITHUB_TOKEN` secret in CI.

### 2.3 Snap / Docker images

**Why:** lower-priority than Homebrew but commonly requested.

**Scope:** small. goreleaser supports both via stanzas. Docker needs a `Dockerfile` (~10 LOC for a static-binary alpine image).

### 2.4 Linux package formats (.deb, .rpm)

**Why:** Linux distros prefer their native package managers over `tar.gz`.

**Scope:** small. goreleaser has `nfpms:` for both formats.

## 3. v0.4 candidates (new work)

### 3.1 CI dryrun on every PR

**Why:** catches `.goreleaser.yaml` drift before tag time. Today the dryrun only runs locally.

**Scope:** add a `.github/workflows/release-dryrun.yml` triggered on pull_request that runs `bash scripts/release-dryrun.sh`. Fail the PR if the dryrun fails.

### 3.2 Smoke-install job in CI

**Why:** confirms the README's binary-download path actually works for users.

**Scope:** post-release workflow that downloads the just-published v* archive, extracts it, runs `--help`. Fails the release if the binary doesn't run on the target OS.

### 3.3 Bench-as-required-check

**Why:** the perf benchmarks (T7.3) have budget assertions but aren't yet a CI gate. A regression that pushes `lint` past 200 ms could land silently.

**Scope:** add a `bench` step to the existing test workflow that runs `go test -bench=. -benchtime=10x -run=^$ ./...` and fails on `b.Errorf`.

### 3.4 Helper-namespace governance (V0.3-PLAN R7 risk)

**Why:** `RECIPES-DSL.md §16` calls helper-namespace evolution a "slow-drip slope." Today there's no documented process for adding a new template helper.

**Scope:** small docs work — add a "Helper Addition Process" section to RECIPES-DSL.md (or a separate governance doc) requiring: docs PR, ≥2 demand cases, schema/CUE update, benchmark.

### 3.5 `dashgen recipe install <url>` (speculative)

**Why:** today users drop YAMLs in `~/.config/dashgen/recipes/` by hand. A package-style installer (`dashgen recipe install github.com/foo/bar/queue-depth.yaml`) would lower the barrier.

**Scope:** medium. Needs URL allow-listing, hash pinning, a manifest format, and a security model. Don't ship without a security review.

**Risk:** opens dashgen up as a potential supply-chain target. Defer unless concrete demand emerges.

### 3.6 Recipe registry / discoverability

**Why:** if user-authored recipes catch on, a community catalog would help. Could be as simple as a `dashgen-recipes-community` GitHub repo with a README index.

**Scope:** zero code; coordination only. Tracked here so it doesn't get lost.

---

## 4. Out of scope for v0.4

- Schema v2 (incompatible breaking changes to the CUE schema). v0.3.x froze the schema as a contract; breaking it requires a v1.0.
- Non-Prometheus metric backends. dashgen is Prometheus-shaped by design.
- Grafana panel-type expansion beyond the existing `timeseries`/`stat`/`gauge` set.
- Replacing CUE with JSON Schema. R1 in V0.3-PLAN tracks this as a fallback if CUE blocks; not a goal.

---

## 5. Sequencing suggestion

If/when this becomes a V0.4-PLAN, suggested first iteration:

1. **§1.1** (ldflags) — 1 hour — unblocks "what version am I running?" for users.
2. **§1.2** (artifact sanity-check) — 30 min — confirms v0.3.0 actually shipped.
3. **§3.1** (dryrun-on-PR) — 1 hour — prevents the next release from breaking silently.
4. **§2.2** (Homebrew) — half-day — biggest distribution win for macOS users.
5. Decide §2.1 (notarization) timing based on user feedback about Gatekeeper warnings.
6. Pick from §3.2–§3.4 based on capacity.

§3.5 and §3.6 stay parked until concrete demand exists.
